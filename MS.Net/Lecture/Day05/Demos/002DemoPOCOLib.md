Detailed mapping explanation
- `Emp` is decorated with `[Table(Name = "Employee")]` telling the generator that this class maps to the `Employee` table.
- Each property uses `[Column(...)]` to describe the corresponding database column name and SQL type.

Flow of execution
- When using an attribute-driven generator:
  1. The generator loads the assembly (e.g., `Assembly.LoadFrom`).
  2. It enumerates types and finds classes with the `Table` attribute.
  3. For each such class the generator inspects properties and collects `Column` attributes.
  4. The generator composes a SQL `CREATE TABLE` statement using the collected metadata and outputs or persists it.

Mapping considerations and recommendations
- Column types in attributes are strings; ensure they are valid SQL types for your target database.
- Consider adding a `IsPrimaryKey` or `IsNullable` flag to the `Column` attribute if you need richer schema generation.
- Consider exposing constructor-based attribute initialization (e.g., `public Column(string name, string type)`) for more concise usage.

Pitfalls
- If a property lacks a `[Column]` attribute the generator should decide a fallback strategy: skip the property, use the property name as column name, or fail with an error. Prefer explicit behavior and document it.
- Name collisions: multiple properties mapping to same column name should be detected and reported.

## If a C# keyword is accidentally removed (what happens)

- Examples:
  - Removing `class` before a type declaration -> `CS1519` or `CS1022` syntax errors.
  - Removing `using` -> `CS0246` type or namespace cannot be found.
  - Removing `public`/`private` changes accessibility; missing access modifier may default to `private` for class members and cause unexpected visibility.
- How to diagnose: Build the project in the IDE or run `dotnet build` to see the compiler diagnostics; use source control to restore the correct version.
